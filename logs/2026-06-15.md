# 2026-06-15 远程大规模实验准备

## 背景

本地 Qwen3.5-2B smoke test 已经能够验证 lifecycle side table、事件流和早期策略路径，但本地短测只能说明代码能跑通，无法支撑“KVFabric 在真实压力下是否有稳定收益”的结论。6 月 15 日开始，项目讨论重点转向远程大规模实验和实验平台建设。

服务器侧由周家润主要负责操作，硬件为 2 x RTX 3090。模型侧计划使用 Qwen3.5-9B 作为主要长测模型，同时保留 Qwen3.5-27B 的探索和对比价值。9B 更适合在双卡 3090 上进行多轮重复实验，27B 用于观察更紧张显存条件下的压力特征。

## 当天确定的方向

### 1. 建立远程实验闭环

需要把一次实验拆成可复现的流程：

- 远程部署代码和依赖。
- 启动 vLLM / KVFabric 服务。
- 按固定 trace 或固定 duration 发送请求。
- 同步服务日志、loadgen 结果、metrics 和 summary。
- 归档 run root，记录配置、时间、模型、策略和退出状态。

这个闭环后续成为 `experiments/long_pressure_benchmark/` 中 deploy、runner、sync、summary 和 run state 工具的基础。

### 2. 重跑早期实验作为对照

早期本地实验主要证明机制存在，实验规模和压力分布与远程 9B 服务差距较大。为了后续比较策略变化，需要在远程环境重跑：

- baseline vLLM 行为。
- shared-aware eviction 的早期版本。
- family-protect 的早期版本。
- 长对话 prefix sharing workload。
- 高压吞吐 workload。

重跑的目的包括校准远程服务器吞吐、确认 GPU 利用率和显存状态、检查日志与指标是否完整，并给 6 月下旬策略迭代提供共同参照。

### 3. 明确 9B 与 27B 的分工

Qwen3.5-9B 后续作为主要实验模型：

- 能在 2 x RTX 3090 上支撑更长时间和更多重复实验。
- 适合跑完整矩阵，便于比较不同 workload 和策略参数。
- 对 SLO goodput、prefix cache、admission 和 scheduler 的变化比较敏感。

Qwen3.5-27B 保留为探索模型：

- 用于观察更高显存压力下的调度和缓存行为。
- 运行成本更高，适合作为补充对照。
- 不作为最终主验收矩阵的唯一依据。

## 发现的问题

1. 本地短测与远程长测之间缺少统一入口。
   当时的脚本更适合手动调试，难以保证每次实验的参数、日志和结果目录结构一致。

2. workload 仍偏人工构造。
   hot/cold 请求比例能够触发 prefix hit，但无法表达 tenant、session、turn、phase 等真实服务结构。

3. 指标偏向 raw throughput。
   仅观察 tok/s 或平均 latency，很难解释某类请求变好、某类请求变差，以及收益来自 admission、eviction 还是 scheduling。

4. 结果归档不足。
   如果服务中途 stalled 或 loadgen partial，仅看输出目录是否存在容易误判实验完成。

## 后续改进计划

- 在 long pressure benchmark 中补齐远程运行脚本和结果同步脚本。
- 将 trace 设计从简单 hot/cold 扩展到 tenant/family/session/turn 结构。
- 增加 class、segment、SLO 和 lifecycle summary。
- 为每个 run 记录配置、状态、heartbeat 和最终 summary。
- 在 9B 上先跑中等规模实验，确认 workload 与 SLO，再进入 12h 长测。

## 阶段意义

6 月 15 日是项目从“机制实现”转向“远程实验验证”的分界点。此后代码迭代不再只围绕单个策略开关，而是围绕远程实验暴露出的系统问题展开，包括请求建模、指标口径、调度公平性、run state、dashboard 和最终矩阵设计。
