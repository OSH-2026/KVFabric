# KVFabric 方案修改建议

KVFabric 的选题非常好，真正价值不在于"改 vLLM 的一个缓存策略"，而在于把 LLM serving 中的 KV Cache 抽象为一种新的操作系统资源：它有页式分配、共享、引用计数、写时复制、驱逐、重算和生命周期管理。你们当前选择先跑通官方 vLLM，再在 Python 控制面验证策略，而不是直接改 CUDA kernel，是正确的工程路线。

但目前项目仍处在 baseline bring-up 和 architecture freeze 阶段，尚未形成真正的 vLLM patch 或策略原型。下一步必须尽快收敛成最小闭环：构造共享前缀 / 模板分叉 / RAG 长上下文 / cache pressure 负载，记录官方 vLLM 的 hit rate、TTFT、TPOT、peak memory 和 eviction 行为，然后增加 lifecycle side table 与 shared-aware eviction policy，对比原始 LRU。

本期不要把独立 C++ runtime 或物理 CoW 作为主承诺。最强交付应该是：一个可复现的 vLLM Python-layer prototype、一套 workload generator、一组清晰指标和一份证明"生命周期感知策略优于普通 LRU"的实验报告。这样项目就能从"调研型报告"成为真正的系统研究型 term project。

KVFabric 是一个非常OS 英才班的项目，但需要从"愿景型 KV Cache runtime"收敛到"可复现、可测量、可比较的生命周期感知 KV Cache 调度原型"。一旦实验闭环跑通，它可以成为模型原生 OS 方向中非常漂亮的 Inference Memory Management 项目。

KVFabric 这个项目比表面上的"KV Cache 优化"更有价值。它涉及的是 **模型原生 OS / AI-OS 里的新型资源管理问题**：在 LLM serving 中，KV Cache 已经不只是推理框架内部的临时缓存，而是类似操作系统中的 **内存页、页表、共享页、引用计数、写时复制、换出/重算策略、调度代价模型** 的一等资源。

项目当前定位是：围绕 LLM serving 中 KV Cache 的调度与生命周期管理，先以 vLLM 为基线，在 Python 控制面验证统一生命周期管理、共享感知驱逐、共享后分叉等机制；长期希望抽象成 C++17/20 实现的可移植 KV Cache scheduler/runtime。仓库 README 明确说明短期以官方 vLLM 基线为中心，重点改造 scheduler / KV cache manager / block pool / metadata 等 Python 控制面路径，暂不优先触碰 C++/CUDA kernel。

当前最大短板是：还没有形成真正的 patch / prototype，核心创新点仍停留在"策略设想 + 基线准备"阶段；下一步建议小步快跑，把"生命周期元数据 + 共享感知驱逐 + 可复现实验负载"尽快落地，完成最小闭环。

## 一、WHAT：KVFabric 到底是什么？——项目解释需要小小修正一下

### 1. 它不是传统 KV store，也不是简单 vLLM benchmark

KVFabric 的名字容易让人误解为分布式 KV 存储或 cache service，但实际不是。它关注的是 LLM 推理过程中的 KV Cache 管理，尤其是：

- KV block 如何分配
- 多请求之间如何复用共享前缀
- 共享后如何分叉
- 显存紧张时如何驱逐
- 驱逐后重算代价如何进入调度决策
- 这些行为如何被观测、计量和优化

项目文档把长期目标定义为"以 C++ 为核心实现语言、面向真实推理系统、强调可移植性的 KV Cache scheduler/runtime"，但当前阶段明确不急于写自研 runtime，而是先在 vLLM 中完成 baseline、代码路径梳理和 Python 控制面原型。

**因此，更准确的项目定义应该是：**

> KVFabric 是一个面向 LLM serving 的 KV Cache 生命周期调度系统原型，短期作为 vLLM Python 控制面 patch，长期演化为可移植的 KV Cache scheduler/runtime。

### 2. 它的核心对象应该是"KV block 生命周期"，不是单个优化技巧

项目研究报告已经提出把每个 KV block 看作生命周期对象，而不是静态显存片段。其状态可抽象为：

```
Create → Populate → Share → Fork → Copy-on-Write → Cooling → Evict → Rebuild
```

报告还建议为 block 维护 `block_hash` / `ref_cnt` / `last_access_ts` / `hit_count` / `share_degree` / `prefix_depth` / `recompute_cost` / `share_state` / `branch_factor` 等 side-table 元数据。

这个抽象非常好。它把项目从"改一个 LRU 策略"提升到"建立 KV Cache 的 OS-style 生命周期模型"。

**建议把项目一句话收敛为：**

> 把 KV Cache 从 vLLM 内部的被动 block pool，升级为可观测、可共享、可分叉、可计价、可调度的一等系统资源。

### 3. 当前实现边界是合理的，但还没有真正进入实现阶段

仓库当前已有：

- vLLM baseline workspace
- offline / online smoke test 脚本
- Qwen 模型预设
- evaluation plan
- architecture overview
- feasibility report
- roadmap
- bring-up log

## 二、WHY：为什么这个项目值得做？

### 1. KV Cache 已经成为 LLM serving 的"新型内存管理问题"

LLM 推理分为 prefill 和 decode。Prefill 建立历史 token 的 K/V 状态，decode 每生成一个 token 都要读取历史 K/V。上下文越长、并发越高，KV Cache 越容易成为显存瓶颈。项目可行性报告也给出了 KV Cache 近似显存公式：

```
M_KV_req ≈ 2 × L × H_kv × D_head × T × s
```

并指出并发请求下总开销会近似叠加。

这在 OS 视角下非常关键：**LLM serving 的瓶颈正在从"纯计算"转向"状态驻留、内存分页、共享、换出、重算、调度公平性"**。

这正是模型原生 OS 应该关心的问题。

### 2. vLLM 是正确的短期平台

vLLM 的 Automatic Prefix Caching 文档说明，它通过 hash-based 方法缓存 KV-cache blocks：每个 block 的 hash 由 block 内 token 和 block 前 prefix token 决定；其基础结构包含 `block_id`、`block_hash`、`ref_cnt` 和 free queue 指针，并在驱逐时使用 LRU 逻辑。

这意味着 vLLM 已经具备 KVFabric 所需的基础对象：

- block
- block table
- prefix hash
- ref count
- free queue
- LRU eviction
- scheduler 与 KV cache manager 边界

项目选择先在 vLLM Python 控制面验证策略，而不是直接改 CUDA kernel，是非常正确的。vLLM V1 已经重构 scheduler、KV cache manager、worker、sampler 和 API server，目标是更统一、更易维护的核心架构。

换句话说：

> vLLM 是"实验基座"，KVFabric 的贡献应体现在 vLLM 之上的生命周期模型、驱逐代价模型和可移植抽象。

### 3. 它和 AI-OS / 模型原生 OS 的连接是成立的

从模型原生 OS 角度看，未来系统需要管理的不再只是 CPU、内存、文件、网络、GPU，而是：

- prompt context
- KV cache
- semantic memory
- tool state
- agent session
- long-context working set
- inference budget
- recomputation cost
- privacy-aware cache sharing

KVFabric 正好切中其中的 KV cache / inference working set / context memory。

它可以被拔高为：

> 面向模型原生 OS 的 Inference Memory Manager 原型。

这个定位比"优化 vLLM prefix cache"更高级，也更适合OS 英才班。

## 三、HOW：当前技术路线如何评价？

### 1. 当前技术路径总体正确

项目 architecture overview 把短期切入点限定在：

- `vllm/v1/core/sched/scheduler.py`
- `vllm/v1/core/kv_cache_manager.py`
- `vllm/v1/core/block_pool.py`
- `vllm/v1/core/kv_cache_utils.py`
- `single_type_kv_cache_manager.py`
- `kv_cache_coordinator.py`
- `vllm/v1/metrics/`

并明确第一阶段避免修改 C++/CUDA attention kernel、底层 KV 物理布局和 slot mapping 语义。

这是非常好的工程判断。因为如果一上来动 kernel，团队很容易陷入：

- 编译成本高
- debug 周期长
- 正确性难验证
- 性能变化难归因
- 无法在 term project 周期内完成闭环

**当前路线更合理：**

| Phase | 内容 |
|-------|------|
| Phase 0 | 跑通官方 vLLM |
| Phase 1 | 读清 scheduler / KV manager / block pool |
| Phase 2 | Python side table 增加生命周期元数据 |
| Phase 3 | 共享感知驱逐策略 |
| Phase 4 | synthetic workloads + metrics |
| Phase 5 | 总结哪些机制值得下沉到 C++ runtime |

### 2. 当前 baseline 做得不错，但存在文档一致性问题

项目已经在 WSL2 + RTX 4070 Laptop GPU 8 GiB + vLLM 0.19.0 环境下完成 offline inference 和 OpenAI-compatible serving smoke test。bring-up log 记录了 OS、kernel、Python、GPU、driver、PyTorch、vLLM 版本，并说明 offline 和 online serving 均通过。

**但这里有一个需要修正的明显问题：**

- README / baseline workspace 里写默认验证模型是 `Qwen/Qwen3.5-2B`
- bring-up log 里实际跑通的是 `Qwen2.5-0.5B-Instruct`

应该修正为：

| 状态 | 模型 |
|------|------|
| Verified baseline | `Qwen2.5-0.5B-Instruct`：已跑通 offline + online |
| Planned baseline | `Qwen3.5-2B`：目标默认 smoke / benchmark 模型，需补充实际验证日志 |
| Optional | `qwen3_5_27b`：RTX 3090 服务器主实验预设，实际使用 `Qwen/Qwen3.5-27B-FP8` |

**不要把"计划模型"写成"已验证模型"。**

### 3. Evaluation Plan 还偏弱，需要修正

当前 evaluation plan 第一阶段关注 official vLLM baseline，指标包括：

- startup success/failure
- model load time
- tokens per second
- request latency
- peak memory usage
- prefix reuse observations
- scripts 是否跨机器可复现

这些是必要的，但还不够。作为 OS term project，指标必须能回答：

> 我的调度策略到底改善了哪一种资源管理行为？代价是什么？边界在哪里？

**建议加入以下核心指标：**

| 类别 | 指标 | 目的 |
|------|------|------|
| Prefix reuse | prefix block hit rate | 衡量共享收益 |
| Saved work | saved prefill tokens | 衡量减少了多少重复计算 |
| Eviction quality | eviction regret | 被驱逐 block 后续是否很快又被重建 |
| Recompute overhead | recomputed token count | 衡量错误驱逐代价 |
| Memory | peak KV blocks / active blocks / cached blocks | 衡量显存压力 |
| Latency | TTFT、TPOT、P50/P95/P99 latency | 衡量用户体验 |
| Throughput | output tok/s、request/s | 衡量服务能力 |
| Scheduling | preemption count、waiting time | 衡量调度副作用 |
| Overhead | Python side-table lookup time | 衡量策略开销 |
| Correctness | output equivalence under deterministic decoding | 保证不改变模型输出 |

尤其要加入一个强指标：

```
EvictionRegret(b) = 1 if block b is evicted and later rebuilt within Δt or N requests
EvictionRegret(b) = 0 otherwise

Eviction Regret Rate = regretted_evictions / total_evictions
```

**这个指标非常适合证明"共享感知驱逐"优于普通 LRU。**

## 四、核心创新分析

### 1. "统一生命周期管理"是最强创新点

这个点成立，而且很有 OS 味道。

传统 vLLM prefix caching 已经有 block hash、ref count、free queue、LRU eviction。但 KVFabric 想进一步引入：

- share degree
- prefix depth
- branch factor
- recompute cost
- lifecycle state
- eviction score

这相当于把 block 从"缓存项"升级成"调度对象"。

**建议将核心贡献明确写成：**

> **Contribution 1: KV block lifecycle metadata model.** 在不修改 vLLM kernel 的前提下，为 KV block 增加生命周期 side table，记录共享、分叉、热度、重算代价和驱逐历史。

### 2. "共享感知驱逐"是最容易落地的贡献

报告提出 KeepScore：

```
KeepScore(b) = w1*Heat(b) + w2*Share(b) + w3*Reuse(b) + w4*PrefixPos(b) + w5*Recompute(b)
```

这个方向非常好，但建议不要一开始就调复杂权重。第一版可以做三种策略对比：

| Policy | 策略 |
|--------|------|
| Policy A | vLLM original LRU |
| Policy B | LRU + ref_cnt/share_degree bias |
| Policy C | LRU + share_degree + prefix_depth + recompute_cost |

最小实现甚至可以是：

```
EvictScore(b) = α*age_rank - β*hit_count - γ*share_degree - δ*prefix_depth_bonus - ε*recompute_cost
```

驱逐 **EvictScore 最高** 的 block，而不是保留 KeepScore 最高的 block。这样和实际 eviction pipeline 更自然。

### 3. "共享后分叉 / CoW"要谨慎定义

项目多次提到 Copy-on-Write 分叉。这个概念与 OS 非常贴合，但在 vLLM 里要谨慎。

PagedAttention 本身已经借鉴虚拟内存思想，把 KV cache 切成非连续 block；vAttention 论文也指出，PagedAttention 通过动态分配 KV-cache 解决碎片问题，但代价是改变 KV-cache 布局，需要 attention kernel 和 serving framework 适配分页。

**因此，在 term project 阶段，不建议承诺真正实现"物理 KV block 的 CoW 拷贝语义"。** 更合理的是分三层：

| 层级 | 内容 | 本期是否做 |
|------|------|-----------|
| L1: Logical Fork | 只记录共享链、分叉点、branch_factor、ref_cnt，不改变物理布局 | ✅ 做 |
| L2: Policy-aware Fork | 对共享后分叉负载，影响驱逐策略和保留优先级 | ✅ 做 |
| L3: Physical CoW | 真正改变 block mapping / copy / slot semantics | ❌ 后续研究再做 |

**本期项目建议做到 L1 + L2。L3 很可能超出 term project 时间范围。**

## 五、主要问题与修改建议

### 问题 1：项目标题和贡献表述还不够"硬"

现在项目容易被理解为：

> 我们要优化 vLLM 的 KV Cache。

这不够强。**建议改成：**

> **KVFabric: Lifecycle-Aware KV Cache Scheduling for Model-Native LLM Serving**

中文：

> **KVFabric：面向模型原生推理服务的 KV Cache 生命周期调度系统**

或者更 OS 化：

> **KVFabric: An OS-style Inference Memory Manager for LLM KV Cache**

中文：

> **KVFabric：面向 LLM KV Cache 的操作系统式推理内存管理器**

这个标题能立刻让大家知道：你们不是做普通缓存技巧，而是在做 **Inference Memory Management**。

### 问题 2：需要明确 threat / workload model

当前项目的问题定义偏性能，缺少 workload model。建议补一页：

| Workload | 场景 | 验证目标 |
|----------|------|----------|
| A: exact shared prefix | System prompt 相同，user prompt 不同 | 验证 vLLM prefix caching baseline |
| B: template-heavy fork | 共同模板 + 少量 slot 变化 + 后续生成分叉 | 验证共享后分叉统计与驱逐策略 |
| C: RAG shared document | 同一篇长文档 + 多个不同问题 | 验证长前缀 block 保留价值 |
| D: multi-turn session | 多个对话 session，有公共历史与私有历史 | 验证生命周期和重算代价 |
| E: adversarial cache pressure | 热点共享请求 + 大量长尾请求混合 | 验证普通 LRU 是否错误驱逐高价值共享 block |

**没有 workload model，驱逐策略就无法证明价值。**

### 问题 3：缺少最小可交付闭环

建议把 term project 的最小闭环改成这个：

```
官方 vLLM baseline
  → 打开 prefix caching
  → 构造 4 类 workload
  → 记录原始 block hit / latency / memory
  → 加 lifecycle side table
  → 加 shared-aware eviction policy
  → 对比 LRU vs KVFabric
  → 画出 hit rate、TTFT、recompute、eviction regret
```

**交付物应包括：**

1. vLLM patch 或 monkey patch
2. workload generator
3. metrics collector
4. benchmark scripts
5. result plots
6. design report
7. limitation section

**这比"未来 C++ runtime"更重要。**

### 问题 4：长期 C++ runtime 现在不宜作为主承诺

Architecture overview 写长期目标是 C++17/20 scheduler/runtime。这个方向可以保留，但不要作为本期验收重点。

**建议明确：**

| 本期目标 | 非本期目标 |
|----------|------------|
| vLLM Python-layer prototype + evaluation | 独立 C++ runtime |
| | CUDA kernel rewrite |
| | physical KV layout change |
| | production serving |

这样评审会觉得项目成熟、风险可控。

## 七、从模型原生 OS 角度的进阶建议

如果要把这个项目提升到"模型原生 OS"高度，应增加一个章节：

### KV Cache as an OS Resource

把 KV Cache 类比为 OS 中的内存页：

| OS 概念 | KVFabric 对应物 |
|---------|----------------|
| physical page | KV block |
| virtual address / page table | request block table |
| page sharing | prefix cache sharing |
| ref count | shared block reference count |
| copy-on-write fork | shared-prefix fork |
| page replacement | KV block eviction |
| working set | active context window |
| page fault | cache miss / recompute |
| swap/reload | KV rebuild / external KV transfer |
| NUMA / device locality | GPU / CPU / remote KV backend |
| page replacement regret | eviction regret |

然后提出：

> 模型原生 OS 需要一个 Inference Memory Manager，KVFabric 是其最小原型。

进一步可以设计四个 OS-style primitives：

```
kv_alloc(request_id, num_tokens)
kv_share(request_id, prefix_hash)
kv_fork(parent_block, branch_id)
kv_evict(policy, budget)
kv_rebuild(block_hash)
kv_account(session_id, token_budget, memory_budget)
```

这会显著提高项目的理论高度。
